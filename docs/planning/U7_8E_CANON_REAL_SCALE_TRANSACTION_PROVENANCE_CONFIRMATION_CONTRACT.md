# U7.8E Canon real-scale transaction provenance confirmation contract

## Document role

This is the prospective execution contract for `U7.8E`. It confirms, on the
exact six already-retained Canon sRAW/mRAW inputs from `U7.8C`, whether the
transaction-scoped software provenance repair proved by `U7.8D` restores a
complete replay-exact real-scale transaction. It does not rewrite or rescue the
authoritative `U7.8C` negative.

## Parent, intervention, and non-goals

- Parent product node: `ULT > U7 > U7.8A-D`.
- Sole intervention: the committed `U7.8D` transaction-scoped software commit
  snapshot and immediate prepublication recheck.
- Controlled baseline: exact `U7.8C` source set, render profile, statistics,
  guardrails, render parameters, output format, failure controls, and resource
  gates.
- The result is not calibrated or physical stock response, Canon colour
  fidelity, image-quality or product-value evidence. It does not open a public
  API, package, installer, release, candidate three, or device claim.
- No threshold, source, order set, compression, tile setting, loader, profile,
  statistics, guardrail, style, failure position, output format, or hash
  normalization may change after this contract is committed.
- The known create-only image/recipe publication question is outside `U7.8E`;
  no product core may change in this leaf.

## Exact historical controls

`U7.8C` executed with a Windows worktree copy of
`configs/film_color_stats.json`. Its Git object is 5,031 LF bytes, while the
frozen runtime file was the deterministic 5,271-byte CRLF materialization.
This is a line-ending representation fact, not a different statistics payload.

Before the first source pixel is decoded, the runner must:

1. read the profile, its legacy profile-config asset, statistics, and
   guardrails from the exact immutable
   `U7.8C` Git objects;
2. verify each Git blob, LF byte count, and LF SHA-256;
3. reject a statistics blob containing any existing carriage return, verify
   exactly 240 LF bytes, replace every LF with CRLF, and verify the exact frozen
   5,271-byte / `1a45e907...7c04` runtime identity;
4. materialize all three runtime inputs only inside the owned scratch root;
5. independently verify that the fixed formal checkout has
   `core.autocrlf=true` and that the profile's three relative asset-ledger
   members under the runtime root are byte exact, including the 5,271-byte
   CRLF statistics worktree file;
6. pass the three scratch render-input paths to the unchanged current
   transaction core; and
7. remove the materialized files and every other owned scratch member before
   the worker exits.

Both formal controllers run from the same fixed checkout and therefore the same
canonical source and scratch path identities. Absolute input/output paths are
an intentional part of every strict recipe and child manifest. Before deleting
each successful publication, the runner must prove that all 18 recipe paths and
all six child-manifest path sets equal those frozen canonical paths. The paths
are not copied verbatim into the order/resource-independent report payload, but
their exact recipe/manifest hashes remain binding there. The machine-local
execution-lock materialization path is never recorded.

- The formal implementation runs from a fresh no-hardlinks checkout of one
  committed implementation commit. The later execution-lock Git object is

- six source hashes exact before and after execution;
- exactly one successful WorkingImage decode per source;
- exactly six children, eighteen RGB16 PNGs, eighteen strict recipes, six child
  manifests, and one aggregate receipt;
- all eighteen recipes bind the one transaction-start software commit;
- software-commit observations are exactly one start snapshot, one
  prepublication recheck, two total, and both equal the formal implementation
  commit;

  decode;
- a complete real batch followed by a late foreign destination preserves only
  the foreign file and leaves no owned publication;
- source bytes remain immutable, network requests are zero, and owned scratch
  residue is zero;
- resource ceilings pass.

## Cross-run gates

Forward and reverse must reproduce exactly:

- all 18 RGB16 PNG SHA-256 values;
- all 18 recipe SHA-256 values;
- all six child-manifest SHA-256 values;
- aggregate receipt SHA-256 and bytes;
- batch ID;
- transaction-scoped software commit and observation counts;
- source set, controls, stable gates, and the order/resource-independent
  scientific identity.

Controller wall time and peak RSS are measured gates but are not byte-identity
fields. Requested source order is not part of the stable scientific payload.
